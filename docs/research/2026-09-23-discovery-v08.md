# Discovery relevance review for the v0.8 pass

Research snapshot: September 23, 2026. This report proposes changes; it does not
establish that they have shipped or passed the final candidate gates. Runtime
implementation and acceptance belong to the current progress checkpoint.

Keep the existing offline MiniSearch backend. The useful next step is better
normalization, match evidence and controlled recovery, followed by measurement.
A new service or model is not justified for this 129-entry catalog. No code,
dependencies, provider calls or shared skills were changed in this research lane.

## Confirmed behavior

Inspected `src/discovery/{intents,lexical-index,service,catalog-schema}.ts`,
`src/tools/discovery.ts`, tests and the existing retrieval experiments. The
installed dependency is MiniSearch 7.2.0. Exact detail lookup is strict and separate
from search; response sizes, paging and query size are bounded. These are good
boundaries to preserve.

The index uses weighted fields, OR combination, and prefix/fuzzy expansion for
every eligible term. It then keeps every positive score and discards the library's
matched query terms, document terms and fields. The service already marks related
entries structurally, but its text presentation omits that distinction. Both agent
skins use that text, so a model cannot reliably distinguish a companion from a
direct lexical match through the normal response.

Read-only probes against the current source reproduced:

| Probe | Observation | Implication |
| --- | --- | --- |
| `ＭｅｓｈＧｅｏ` | Zero results | NFKC runs after ASCII camel-case splitting, leaving `meshgeo` unsplit. |
| `UVAtlas` and `ＵＶAtlas` | Both tokenize as `uvatlas` | Acronym-to-word boundaries are not handled. |
| `bevel only selected edges` | `subdivide` first of 19 candidates | Its summary says it does **not** do selected-edge beveling. Negative explanatory text supplies positive lexical evidence. |
| `solve turbulent fluid equations with adaptive timesteps` | `parametricSurface` is the only result | One partial lexical match cannot establish the requested capability. |
| `transcribe speech to phonemes in real time` | Rubber recipe first of 17 candidates | Incidental words and approximate matches produce noise. |
| `create a soft body simulation` | Joint-chain assembly first of 38 candidates | Generic construction words swamp an unsupported simulation request. |

These probes are now observed regression cases. The earlier fresh 16-query review
found all 12 supported requests in the first five but candidates for all four
unsupported requests. Its 0.753 MRR and desktop performance figures remain
historical measurements, not results for a revised algorithm. See the
[cutover report](../reviews/2026-09-23-cutover-acceptance.md#fresh-discovery-observations).

## Primary-source findings and choice

MiniSearch already exposes matched query terms, document terms and fields. Its
existing API also supports per-term recovery controls and field boosts. The
upstream documentation recommends using field boosts before tuning BM25+
internals. These are enough to implement and explain the proposed changes without
another dependency. [Result evidence](https://lucaong.github.io/minisearch/types/MiniSearch.SearchResult.html),
[search controls](https://lucaong.github.io/minisearch/types/MiniSearch.SearchOptions.html).

Typesense 30.2 provides an instructive design: typo expansion and token dropping
are controlled independently, exact matching is prioritized, and prefix matching
primarily serves the last incomplete word. Adopt the distinction between precise
retrieval and relaxed recovery, not its server deployment or default token
dropping. Agent queries are usually complete requests, not interactive keystrokes.
[Current search API](https://typesense.org/docs/30.2/api/search.html).

Elasticsearch's conditional minimum-match mechanism demonstrates that multiword
search need not be an unqualified OR. A Kiln policy should still be evaluated
against long natural-language queries and partial useful operations; copying a
percentage blindly would remove useful matches.
[Minimum-match semantics](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-minimum-should-match).

Orama is a credible embedded alternative with full-text BM25, field weighting,
stemming and optional vector/hybrid search. FlexSearch offers configurable
normalization and matching encoders. Neither feature list establishes better
Kiln relevance; both would require rerunning identical judgments and migration
tests. The current backend already exposes the missing controls, so a replacement
adds work without demonstrated benefit.
[Orama project](https://github.com/oramasearch/orama),
[FlexSearch project](https://github.com/nextapps-de/flexsearch).

The prior neural experiments already measured their particular recall gains and
substantial CPU/model costs. Do not repeat that survey or impose those costs on
users. Precomputed catalog embeddings alone still do not encode an arbitrary new
query. [Existing offline decision](../reviews/2026-09-21-discovery-offline-decision.md).

## Minimal implementation proposal, in priority order

1. Normalize NFKC before identifier splitting; handle acronym boundaries and a
   small reviewed set of technical inflections such as UVs. Keep exact ID lookup
   case-sensitive and literal. Test Unicode identifiers, dimensions, axes and
   units; do not add a broad stemmer that conflates operations.
2. Preserve match evidence through the index/service boundary. Render concise
   matched terms and a distinct related-entry label in the model-facing text, not
   only structured JSON. Keep scores internal. A statement such as “matches
   `profile` and `path`; other request terms unmatched” is evidence, not a
   confidence percentage or a capability verdict.
3. Compare an exact-token pass with controlled recovery for missing terms. Avoid
   adding typo/prefix candidates merely to fill a page. Recovery should remain
   available when one generic exact hit exists, because that hit must not suppress
   correction of the actually important misspelled word. Keep deterministic ties,
   exact named operations, bounded expansion and complete-query processing.
4. Use reviewed positive names, aliases and intent phrases as stronger evidence
   than explanatory summary prose. In particular, a summary-only match on a
   negated limitation must not be presented as direct support. Keep the limitation
   visible. Do not attempt a fragile general-purpose negation parser or delete
   safety wording just to improve ranking. If structured positive search text is
   added, require it during catalog review rather than duplicating prose ad hoc.
5. Treat weak/partial matches honestly and make zero-match responses actionable:
   suggest a narrower operation query, exact contract lookup, overview browsing,
   or custom geometry. Low scores and unmatched terms cannot prove that a request
   is impossible. Do not advertise semantic abstention, automatic capability
   certification or general natural-language negation understanding.
6. Add related entries only as bounded, labeled companions to selected seeds.
   Verify filters and pagination still apply. Do not impose one result per family
   or recipe quotas: alternatives within one family can be exactly what a model
   needs. If near-duplicate axis variants crowd a page, evaluate relation-aware
   grouping separately rather than hiding useful exact matches.

Steps 1–2 are direct correctness/presentation fixes. Steps 3–5 change retrieval
policy and must earn adoption on comparisons. Numeric minimum coverage or relative
score cutoffs are hypotheses, not established constants. A rare valid concept may
match once; a wholly unsupported request can match many generic words.

## Proposed evaluation queries

The following judgments were authored before execution of these queries in this
lane. The author read the catalog and older judgments, so this is an independently
authored supplement, **not** a blinded benchmark. Freeze it before implementation
tuning. Expected helpers are acceptable candidates, not exhaustive result sets;
alternative correct constructions should be adjudicated from contracts.

| Query | Acceptable candidates / expected treatment |
| --- | --- |
| rounded loot crate with exact exterior dimensions | `roundedBoxGeo` |
| rescale texture repetition without reshaping the mesh | `remapUV` |
| duplicate an animated trap mechanism without sharing mutable geometry | `replicateAssembly` |
| copy a sword material before recoloring just the blade | `copyMaterial` |
| carry a square section along a bent power conduit | `sweepProfile` |
| grow a shape through several matching polygon outlines | `loftProfiles` |
| form a potion bottle by spinning a closed profile | `revolveProfile` |
| animate a treasure chest lid around its authored hinge | `rotationTrack`, `createPivot` |
| keep roof shingles tangent to the sloping roof faces | `createRoofSurfaceLayout` |
| mirror an elbow guard across the local z plane | `mirror` |
| make the fins from a leaf alpha mask on a flat card | `foliageCardGeo`, `foliageMaterial`, `recipe:foliage-cutout-v1` |
| connect a diagonal brace between two moving mounting coordinates | `beamBetween`, `recipe:joined-frame-v1` |
| swepProfile square section | `sweepProfile`, with correction evidence |
| projet UV cylindrical wrapping | `projectUV`, with correction evidence |
| retopologize a scan into production quad loops | No implemented retopology claim; partial geometry guidance must be labeled. |
| simulate river currents pushing a floating crate | No fluid/dynamics implementation claim. |
| bake multiplayer network prediction into a door | No networking implementation claim. |
| certify castle wall load capacity | No structural certification claim. |
| create a pivot for a door and simulate rigid body collisions | Useful pivot retrieval is allowed; collisions are not thereby implemented. |
| subdivide without changing the silhouette or UV seams | Retrieve its contract and expose the smoothing/UV limitations; keyword coverage cannot guarantee preservation. |

Measure supported top-1/top-5 success and reciprocal rank separately from harmful
unsupported suggestions. Inspect whether the actual CLI/MCP text exposes partial
and related evidence. Retain the original observed query sets as regression data;
do not rename them fresh holdouts. New AGY runs should test whether models fetch
the right contracts and successfully use them, rather than only counting hits.

No new service, model or dependency is proposed. Two-stage retrieval may roughly
double the index work; measure it rather than assuming negligible cost. Recheck
cold installed CLI startup and warm queries on the connected lower-power machine,
without network/provider keys, and record response bytes. Existing index-only
engineering targets remain p95 below 25 ms, initialization below 250 ms and added
heap below 32 MiB at 1,000 synthetic entries; these are not total CLI budgets or
quality claims. Preserve query/response limits and bump the index identity when
ranking behavior changes.
