## Phase 1: establish common composition contracts

**K07: Part/assembly conformance contract.** Reuse existing semantic metadata. Specify local frames, attachment interfaces, material slots, origin, bounds, hierarchy, ownership, and stable role identity. Distinguish a geometry, mesh, assembly, and scene. Use wheel, roof, structural bay, and articulated mechanism as different clients. Acceptance: replace a compatible part without rewriting neighbors; repeat assemblies without losing geometry, frames or roles. Animation names and relationship targets must be remapped coherently. Shared geometry should remain shared where intended. Preserve legacy mesh-only instancing behavior separately.

**K08: Atomic helper contract schema.** Extend the existing catalog rather than creating another registry. Useful fields: units, axes, origin, sync/async, ownership, input/output kind, topology prerequisites, preserved/dropped attributes, parameter bounds, limitations, stability, related operations, and executable fixture references. Generate human and agent views from the same source. Start with operations involved in confirmed failures; do not block useful repairs on perfect metadata for all 105 helpers.

**K09: Composition regression matrix.** Test meaningful cross-products: primitive → deformation → normals → export; profile → sweep/loft → UV/material → export; CSG with and without preservation; hierarchy → repeat/mirror → semantic inspection; part replacement → animation. Include seam, negative-scale, transformed-parent, thin-feature, empty-result and nonfinite inputs. Test documented destructive operations as destructive; do not assert universal attribute preservation. The goal is contract conformance, not a redundant test for every line of implementation.

K07/K08 can inform each other. K09 grows from observed defects. New generic attachment/replication helpers should be justified by these cases, not designed as a speculative universal CAD framework.

## Phase 2: requirements-first host workflow

**K10: Versioned requirements binding.** Add a host-owned policy channel for CLI and MCP. Establish requirements from the brief outside generated source, echo them in results, retain them with lineage, and carry them through edits/save/export/import according to a documented portability policy. Preserve legacy category behavior through an adapter. Separate semantic labels, asset scope, required behavior, and geometry/export requirements. Unknown is distinct from false. Never treat omitted capabilities as permission to discard existing obligations.

Acceptance cases: mislabeled source; absent intent; CLI typo; source revision trying to lower requirements; reopening a saved asset; importing old metadata; one program used under two explicit review profiles. A separate intent-tool call by the generating agent does not itself authorize lowering obligations: that requires a host-authorized policy change with provenance. Review caches and candidate validity for policy identity as well as source identity. A requirements change must not silently reuse a prior validation result from another policy.

**K11: Remove house assumptions from the new neutral path.** Architecture label alone must not invent a roof, storey count, or navigation promise. Required limits must distinguish computational safety from supported semantic validation. Preserve runtime bounds; unsupported topology should report limited validation rather than silently claim success. A six-level facade, open coliseum, roofless ruin, dome, and miniature should all receive coherent policies. This does not require implementing all of them as new presets.

**K12: Evaluate discovery improvements.** Keep current overview/search/exact-name retrieval. Add synonyms, prerequisites, failure guidance and related operations from K08. Test unfamiliar operation requests and misleading category terms. Success means relevant helpers selected and used correctly with lower repair burden, not simply shorter prompts. Specialist recipe suggestions remain available to novices and models. K12 can begin before K10, but discovery must never independently rewrite trusted policy.

## Phase 3: qualify the product, then simplify integrations

**K13: Blind authoring/edit benchmark.** Run the three conditions in the main report with repeated matched briefs and held-out compositions. Requires separate authorization for live model/subscription use. Store failed attempts as well as successes. Review actual rendered images, source edits, geometry diagnostics, semantic structure, material fidelity and destination imports. Track the 42 example-gap helpers as candidates, not as a quota demanding all be used.

First campaign: familiar prop control; rotated/scaled repeated mechanism; steerable wheel assembly; boat without wheel assumptions; multi-level facade; open coliseum; foliage/cloth surface; modular bridge or terrain tile. Include swap, resize, repeat-count and material edits. Use more than one model/harness when budget permits, and distinguish harness effects from model effects. First establish baseline variance; then select a larger confirmation sample around consequential differences.

**K14: Strands program-reference adapter.** Wire the existing full-program registry adapter as an opt-in runtime surface. Verify terminal submission refers to the exact tested revision; carry trusted policy, cancellation, budgets, image receipts and provider cache semantics. Run offline adapter tests before live qualification. Do not infer dependency compatibility from a version range alone. Retire old surfaces only after measured parity or publish a clear deprecation path if maintaining them is not worthwhile.

**K15: Evidence-based additions and retirement.** Potential additions: frame-to-frame attachment, assembly-safe repetition, multiple panel openings, profile/bay/seating recipes. Add only those that reduce observed failures or substantial repeated custom code. Consolidate duplicate operations when parameter meaning and behavior really match. Retain compatibility aliases temporarily with explicit deprecation. Keep experimental shell/bevel/remesh tools outside stable claims until accuracy, topology, attributes and resource behavior have defensible limits.

## Proposed packaging support levels

These are recommendations, not assertions of current certification.

| Level | Scope | Evidence needed |
| --- | --- | --- |
| Primary | Host-agent authoring through CLI/MCP, source revisions and GLB delivery | Offline package gates plus representative current authoring/edit/import receipts |
| Supported operation | Individual helper with a clear documented contract | Focused conformance and export tests; visual/material evidence where relevant |
| Qualified recipe | Domain assembly or workflow promoted for broad use | Repeated agent use and composition/parameter-edit acceptance, not only synthetic unit fixtures |
| Experimental | Implicit and advanced geometry, unqualified adapter combinations | Explicit limitations, bounded execution, opt-in behavior and retained experimental receipts |

Do not equate “105 exported functions” with 105 independently battle-tested workflows. Conversely, do not hide all vehicles or architecture merely because a category lacks broad model evidence: disclose the actual operation and recipe support level.

## Decision checkpoints

1. After Phase 0, decide whether packaging claims match the remaining known limitations.
2. After K07–K09, assess whether parts actually compose; defer catalog expansion if they do not.
3. After K10–K13, compare neutral discovery with category/recipe guidance. Retain whichever guidance improves results without silently selecting policy.
4. After K14, choose whether Strands merits ongoing first-class qualification, optional maintenance, or staged retirement.

No engine rewrite, new neural backend, CAD kernel, general constraint solver, world runtime expansion, or mass helper deletion is proposed as an immediate packaging requirement.
