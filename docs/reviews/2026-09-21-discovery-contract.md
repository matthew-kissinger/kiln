# Discovery contract and retirement decisions

Implementation baseline: b81cfd4caed64bd90547ff83b4e513e59a1d4913. This records D01/D02 and the discovery portion of L01; it is not a completion claim for the remaining retirements.

The only new callable name is `kiln_discover`, exposed by the shared registry; CLI uses `kiln discover`. The old registry entry and package export are removed. The shared typed catalog is authoritative; no old callable alias or alternate response dialect ships. See the [checkpoint](../plans/2026-09-22-progress-checkpoint.md) for remaining acceptance.

Discovery runs in-process on CPU, offline, without model weights, an inference runtime, a search service, provider keys or automatic downloads. Its supported lexical implementation has measured offline query evidence; fresh recipe judgments and installed qualification remain open. Neural research challengers remain research artifacts; an optional future enhancement needs a separate adoption decision. See the [offline search decision](2026-09-21-discovery-offline-decision.md).

Requests are strict and versioned by their schema/response contract. Mutually exclusive modes are overview (default), search, exact detail batch, and capabilities. Search accepts a natural-language query plus optional family/kind/tag filters, with deterministic offset pagination. Exact IDs are case-sensitive and never typo-corrected into execution. Unknown IDs return suggestions plus an error. Search summaries disclose limitations and distinguish direct from related matches; scores are internal diagnostics, not confidence. Detail uses `ids` with at most six unique stable IDs or exact executable names and returns typed full entries. The retired `name`, `names` and `category` selectors are rejected. Overview and search return compact summaries, never executable examples or full contracts, with six entries by default and twelve maximum per page. Capabilities come from the current host, not the static catalog. The executable request schema is `src/discovery/query-schema.ts`; registry/CLI/native integration is implemented.

Entry IDs are namespaced: `operation:<name>`, `assembly:<name>`, `recipe:<slug>`. A name remains the executable sandbox identifier where applicable. Entries carry version, kind, family, tags, aliases, intent phrases, stability and typed related links. Operations and assemblies carry contracts including signatures, returns, units, axes, origin, ownership, coordinates, parameter bounds, topology, preservation, semantic effects and cost. Recipes carry prerequisites, steps, source examples, adaptation points and limitations. Unknown contract facts must remain explicit rather than be invented by metadata generation.

Registry, CLI, agent context, current skills, workspace creation, exports and generated reference now use this contract; final installed-package and complete migration acceptance remain separate. The old `category` discovery selector is rejected; its replacement is `family` for grouping and `tags` for semantic labels. `listPrimitives()` and its package subpath are removed; the catalog supplies the shared implementation.

MiniSearch 7.2.0 is selected and implemented after the D13-D18 comparisons. The remaining relevance/holdout qualification is tracked under D18; research challengers remain outside the production dependency graph. The benchmark fixes relevance judgments before tuning and uses identical metadata across candidates. New catalog entries must be validated before indexing, including unique IDs and non-dangling related references.
